# ftCo_80095EFC: aggregate storage breaks a register-allocation plateau

Learned from Mark McCaskey's upstream match, commit
`0b03df6f86ec9def3452db0369766da847c99ca5`, PR
https://github.com/doldecomp/melee/pull/3325.
Controlled verification performed on fork commit `9ff28561ee`.

## What actually worked

The landed source represents the throw scale as a one-field aggregate:

```c
struct {
    /* +0 */ float value;
} scale;
scale.value = 1;
```

All subsequent scale updates and reads use `scale.value`. The matched function
uses direct frame-speed division and interpolation expressions, and a
three-argument `pl_8003E978` call. The old version's seven unused floating-point
call arguments, frame-speed inline, and intermediate speed locals are gone.
The commit also fixes symbol/constant layout and links the translation unit;
those integration changes should not be confused with the isolated storage test.

## Controlled evidence

Starting from the landed source, change only the aggregate declaration to
`float scale;`, retain the separate `scale = 1;` assignment, and replace every
`scale.value` access with `scale`. Leave expressions, call signature, symbols,
and all other source unchanged. Compile using:

```sh
python tools/checkdiff.py --format compact ftCo_80095EFC
```

| Source | Match | Frame | Result |
| --- | --- | --- | --- |
| Landed aggregate | 100.00% | 88 bytes | Instruction-identical |
| Scalar-only ablation | 99.41% | 80 bytes | Same opcode sequence; 17 differing stack-reference pairs and eight FPR-only pairs |
| Aggregate restored | 100.00% | 88 bytes | Instruction-identical again |

Thus aggregate versus scalar storage demonstrably affects both frame allocation
and floating-point register choices in this compiler/context, even though both
sources perform the same arithmetic. This is not just padding: the scalar
variant also changes register operands. This test does not establish the exact
optimizer pass or allocator graph edge responsible, nor prove that the original
HAL source contained this struct. Internal causality needs paired compiler traces.

## Why our previous best was misleading

Our earlier source reached 99.85% with an 88-byte frame and four FPR-only
differences: the denominator and X load used f0/f1 in the opposite assignment,
with corresponding divide/subtract uses. That version retained the extra call
arguments, inline, and scalar chain. A correct opcode sequence and frame did not
establish that those source choices were correct.

Allocator replay describes the graph generated by a particular source. It can
rule out color/order changes within that graph; it cannot rule out another
source representation that creates a different graph. Similarly, repeated
declaration/lifetime experiments on the same scalar source family do not exhaust
aggregate storage combined with simpler expressions and a corrected signature.
Do not claim aggregate storage alone transforms our old plateau into a match:
the controlled ablation above uses the final upstream context, not the old one.

## Reuse on similar functions

1. For a persistent FPR swap or unexplained stack reservation, include scalar
   versus one-field aggregate storage as a bounded source experiment, especially
   for a scale/accumulator initialized before a conditional update and consumed
   later. Preserve initialization style and arithmetic while testing it.
2. Revisit call signatures using callee evidence. Residual values in argument
   registers do not by themselves prove floating-point parameters exist. Extra
   arguments can constrain lifetimes/allocation and create a misleading plateau.
3. Test these choices on simple source as well as the current highest-scoring
   source. A temporary score drop may expose the correct source family.
4. Check raw operands, frame size, and neighboring/callee functions; do not accept
   normalized opcode identity as a full match or add padding based on score alone.
5. Preserve the aggregate comment once matched so a later cleanup does not
   silently replace it with a scalar and regress code generation.

Searchable database pattern: `single-field-aggregate-fpr-allocation`.
This is a verified single-function example, not a universal MWCC rule.
